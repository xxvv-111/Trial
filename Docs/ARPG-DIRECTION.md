# 方向变更可行性分析：房间制 → ARPG 单场景

> **变更请求**：放弃《哈迪斯》式"三房间清怪"结构，改为**一个完整场景、一条连续通路直达 Boss，沿途布置小怪**。
>
> 本文回答：**可行吗？要动多少？会变简单还是变难？有哪些坑？**
> 所有"现状"均为实机核对，非照抄旧文档。
>
> 最后更新：2026-10-04 | 状态：**待你决策**（有 5 个阻塞项，见 §6）

---

## 0. 结论先说

| 判断 | 答案 |
|---|---|
| **技术可行吗** | ✅ **完全可行**。所需能力（敌人 AI、战斗、相机、HUD、NavMesh）**全部已有或已装包** |
| **代码要大改吗** | 🟢 **不用，改动比想象小。** 现有 `RoomController` 本质就是"进入区域→刷怪→清空→开放通路"，**换个语义就是 ARPG 的遭遇点** |
| **会让总工作量变少吗** | ❌ **不会。这是"范围转移"，不是"范围缩减"** —— 见 §2 |
| **最大的风险** | 🔴 **Boss 从"可延后"变成"必须做，且在关键路径上"** —— 而 Boss 招式表至今未定 |
| **最大短板** | 🔴 **敌人只有 1 种外观（纯白无贴图）**，"一路小怪"视觉上会单薄 |
| **建议** | ✅ 做，但**采用"混合方案"**（§5）：保留区域触发机制当作遭遇点，不做成完全连续 —— 否则玩家能**一路跑过所有怪直奔 Boss** |

## 1. 先纠正一个前提：现在的敌人是"可见的白模"

这直接影响"路上放小怪"的观感判断，所以先说清。

| 预制体 | Renderer | 网格 | 材质贴图 |
|---|---|---|---|
| `Boxer` | 1 个 `SkinnedMeshRenderer` | `STYLIZED-BASEMESH-BIGMALE-OBJ` | ❌ **空**（`_BaseColor` 纯白） |
| `Gunner` | 1 个 `SkinnedMeshRenderer` | **同一网格** | ❌ 空 |
| `Enemy_Slime` | 1 个 `MeshRenderer` | Unity 内建球体 | ✅ `Mat_Slime` |

**所以敌人能跑能打能播动画，只是全白。** 这不阻塞玩法，但：

> ⚠️ **`Boxer` 和 `Gunner` 用完全相同的网格** → **当前实际只有一种敌人外观**。
> 单场景 ARPG 要"沿途一路小怪"，靠一种白模会显得重复。
> 💡 **低成本解法**：同一网格 + 不同材质（换色/金属度）+ 不同缩放 → 做出"小兵 / 精英 / Boss"的视觉层级。

## 2. 工作量：是"转移"不是"缩减"

这是本次决策最需要看清的一点。

| | 原方案（房间制） | 新方案（ARPG 单场景） |
|---|---|---|
| 关卡空间 | 3 间房（约 20×20 每间） | **1 条长通路**（需更长，含起始区/多个遭遇区/Boss 区） |
| 空间工作量 | 小（现有白盒） | **更大**（要设计路径、开阔地、隘口、Boss 场地） |
| 节奏设计 | ✅ **白送**——"清完开门"天然控制节奏 | ⚠️ **要手动设计**——敌人在哪、多少、怎么挡住玩家 |
| 区域逻辑代码 | 已有 `RoomController` | 🟢 **可复用**，改语义即可 |
| 敌人数量/波次 | 每房 1–2 个，简单 | ⚠️ 更多敌人同屏 → 要考虑**性能与对象池** |
| NavMesh | 3 间小房 | ⚠️ **更长更复杂**的导航网 + 巡逻 + 追击范围 |
| Boss | 3–5 天（原 M4） | 🔴 **同样 3–5 天，但变成"必须做"** |

**结论**：代码省一点，**关卡与节奏设计要多花**。总量**持平偏增**。

> 关键点：**房间制把"节奏"这件事白送给你了**——玩家必须清完才能走，天然控制战斗密度。
> 单场景连续通路必须**手动设计节奏**（哪里放怪、是否封路），这是新增的设计成本。

## 4. 新增/要改的部分

### 4.1 关卡几何（新增）

- **场景**：新建一个关卡场景（或改造现有 `Game.unity`）
- ⚠️ **ProBuilder 未安装**（实测不可用）→ 要么用 **Cube 拼白盒**，要么装 ProBuilder
- 需要：起始区 → 通路（含开阔地与隘口）→ Boss 区；**沿途障碍物**（NavMesh 与视野遮挡依赖它们）

### 4.2 NavMesh（从"小"变"大"）

- 现状：**0 个 `NavMeshAgent`、导航网未烘焙**（实测）
- 新方案要：**整条通路一次性烘焙** + 敌人巡逻 + 追击边界（⚠️ 不能让敌人追出整张图）
- 详见 `NAVMESH-GUIDE.md`

### 4.3 敌人布置与节奏（新增的设计工作）

- 敌人**放置点 / 巡逻路径 / 触发式刷怪**
- ⚠️ **同屏敌人变多** → 需要评估性能（当前对象池只服务于特效，敌人是 `SetActive` 管理）

### 4.4 Boss（⚠️ 从"可延后"变成"关键路径"）

**这是本次变更影响最大的一项。**

- 现状：**没有任何 Boss 资产、没有任何 Boss 脚本**。`BossDied` 事件存在，但只是"最后一间房清空"时被 `RoomController` 触发，**名不副实**
- 原规划：M4，3–5 天，招式表"暂缓"
- **新方案下**：Boss 是**整条路的终点与目标**，**不能再延后**，否则"通往 Boss"这个设计没有落点
- 且**Boss 模型也没有**（可用敌人网格放大 + 换材质顶替，见 §1）

### 4.5 要删/改的旧东西

| 项 | 处理 |
|---|---|
| `RoomController.isFinalRoom` → 触发 `BossDied` | ⚠️ 语义错误，需改为真正由 **Boss 死亡**触发 |
| "Clean The Room" / "Door Open" 提示 | 文案需改（现在是英文硬编码） |
| HUD "房间 N/3" | 去掉，改为进度或直接不要 |
| 门锁机制 | 见 §5 的取舍 |

## 5. ⚠️ 新方案有一个必须先解决的设计问题

> **"一条开阔通路 + 沿途小怪"意味着：玩家可以完全不打小怪，一路跑到 Boss。**

这不是 bug，是这类设计的固有特性。必须选一种处理方式：

| 方案 | 做法 | 代码成本 | 体验 |
|---|---|---|---|
| **A. 硬性封路（推荐）** | 每个遭遇区入口落闸，清完才开 —— **就是现有 `RoomController` 逻辑** | 🟢 **几乎为 0**（复用） | 节奏可控，最接近原设计的可靠性 |
| B. 软性阻拦 | 用敌人站位/狭窄地形自然阻挡，不强制 | 🟡 中（纯关卡设计） | 更自由，但会被跳过 |
| C. 不阻拦 | 允许跑酷直奔 Boss | 🟢 0 | ⚠️ 玩家会跳过你 80% 的设计内容 |
| D. 混合 | 多数区域软拦，Boss 前一个硬闸 | 🟡 中 | 平衡 |

**我的建议：A 或 D。**

理由：你现有的 `RoomController` **本身就是方案 A 的完整实现**——"玩家进入 → 关门 → 刷怪 → 全清 → 开门"。
**它不需要被推翻，只需要被重新理解**：把"房间"改叫"遭遇区/战斗区"，把"门"改叫"闸门"，
中间用通路连起来而不是紧邻排列。**这样代码几乎不用改，只改关卡布局与命名。**

## 6. 🔴 阻塞项：开工前必须拍板

| # | 事项 | 为什么阻塞 |
|---|---|---|
| **1** | **Boss 招式表**（4 个招式名 + 判定形状 + 前摇时长） | ⚠️ **现在是关键路径**。Boss 从"最后一间房"升级为"整条路的终点"，不定就没法排 M4，而 M4 不能延后 |
| **2** | **是否封路**（§5 的方案 A/B/C/D） | 直接决定要不要复用 `RoomController`、关卡怎么摆 |
| **3** | **关卡规模**（多长？几个遭遇区？） | 决定 A 方案下的闸门数量、NavMesh 复杂度、Boss 场地大小 |
| **4** | **Boss 模型来源** | 目前**零 Boss 资产**。可选：放大敌人网格换色 / AI 生成 / Sketchfab |
| **5** | **敌人外观是否投入** | 现在只有 1 种白模。接受"换色变体"还是做新模型？ |

## 7. 建议的实施顺序

> 注意：**M1（系统骨架）和 M2（武器）与关卡结构无关，照做不误。** 方向变更主要影响 M3 及以后。

| 阶段 | 内容 | 受本次变更的影响 |
|---|---|---|
| **M1 系统骨架** | 体力出口 ✅已完成 / Hitbox / 暂停 | 🟢 **无影响**，照做 |
| **M2 武器** | 剑·插地 / 长枪·投掷召回 | 🟢 **无影响**，照做 |
| **M3 敌人 + 寻路** | NavMesh / 视野 / 敌人状态机 | 🟡 **范围变大**：加巡逻、遭遇区刷怪、追击边界 |
| **M3.5 关卡（新增）** | 搭通路白盒 + 障碍物 + 烘焙 + **闸门布置** | 🆕 **新阶段**（原方案里这一步很轻） |
| **M4 Boss** | 招式表 → 决策层 → 招式层 → 阶段 → 血条 | 🔴 **升级为关键路径，不可延后** |
| **M5 收口** | HUD（**去掉房间进度**）/ 音频 / 存档 / 构建 | 🟡 小幅调整 |
| **M6 文档** | 报告 / PPT / 视频 | 🟡 报告需增"方案选型"章节（房间制 vs 单场景 ARPG 的取舍，**这是加分项**） |

**建议起点：先定 §6 的第 1、2 项**，然后按 M1 → M2 推进（这两阶段与方向无关，可以立即开工）。

## 8. 一句话总结

> **技术上完全可行，代码改动比预想小**（现有房间逻辑可直接改语义复用），
> 但要认清两件事：
> ① **这是范围转移不是缩减** —— 关卡与节奏设计的工作量上来了；
> ② **Boss 现在是最硬的瓶颈** —— 它从"最后一间房"变成"整条路的目标"，必须最先定义。
