## 0. 结论先说

### ⚠️ 最终结论：**未采纳**，改用多关卡独立场景（2026-10-05）

- 本方案的核心卖点"一条开放通路"，**恰好取消了房间制白送的节奏控制**（清完才开门），

## 1. 先纠正一个前提：现在的敌人是"可见的白模"

这直接影响"路上放小怪"的观感判断，所以先说清。

| 预制体 | Renderer | 网格 | 材质贴图 |
|---|---|---|---|
| `Boxer` | 1 个 `SkinnedMeshRenderer` | `STYLIZED-BASEMESH-BIGMALE-OBJ` | ❌ **空**（`_BaseColor` 纯白） |
| `Gunner` | 1 个 `SkinnedMeshRenderer` | **同一网格** | ❌ 空 |
| `Enemy_Slime` | 1 个 `MeshRenderer` | Unity 内建球体 | ✅ `Mat_Slime` |

**所以敌人能跑能打能播动画，只是全白。** 这不阻塞玩法，但：

> ⚠️ **`Boxer` 和 `Gunner` 用完全相同的网格** → **当前实际只有一种敌人外观**。
> 单场景 ARPG 要"沿途一路小怪"，靠一种白模会显得重复。
> 💡 **低成本解法**：同一网格 + 不同材质（换色/金属度）+ 不同缩放 → 做出"小兵 / 精英 / Boss"的视觉层级。

## 2. 工作量：是"转移"不是"缩减"

这是本次决策最需要看清的一点。

| | 原方案（房间制） | 新方案（ARPG 单场景） |
|---|---|---|
| 关卡空间 | 3 间房（约 20×20 每间） | **1 条长通路**（需更长，含起始区/多个遭遇区/Boss 区） |
| 空间工作量 | 小（现有白盒） | **更大**（要设计路径、开阔地、隘口、Boss 场地） |
| 节奏设计 | ✅ **白送**——"清完开门"天然控制节奏 | ⚠️ **要手动设计**——敌人在哪、多少、怎么挡住玩家 |
| 区域逻辑代码 | 已有 `RoomController` | 🟢 **可复用**，改语义即可 |
| 敌人数量/波次 | 每房 1–2 个，简单 | ⚠️ 更多敌人同屏 → 要考虑**性能与对象池** |
| NavMesh | 3 间小房 | ⚠️ **更长更复杂**的导航网 + 巡逻 + 追击范围 |
| **Boss** | 3–5 天（原 M4） | 🟡 **同样 3–5 天，但决策改为"留到最后"**（C 方案下不再卡关键路径，但需守住时间预算） |

**结论**：代码省一点，**关卡与节奏设计要多花**。总量**持平偏增**。

> 关键点：**房间制把"节奏"这件事白送给你了**——玩家必须清完才能走，天然控制战斗密度。
> 单场景连续通路必须**手动设计节奏**（哪里放怪、是否封路），这是新增的设计成本。

### 4.6 相机 ✅ **已实现**（2026-10-04 落地；2026-10-05 加入仰视与地面安全角）

**需求演进**：跟随主角 → 鼠标控制视角 → 越肩 → **俯角可仰视的后置跟随（当前）**。

| 项 | 当前实现 |
|---|---|
| 机位算法 | 焦点 = 角色 + `_focusHeight(1.0)`；机位 = 焦点**沿视线后退** `_distance(3)` → **视线必然穿过角色，角色永远居中不出画** |
| 朝向 | ⚠️ **相机 yaw 归鼠标控制，不跟随角色**（`_followTargetYaw = false`）—— 原因见下方「三者互不驱动」 |
| 开局对齐 | `_alignYawToTargetOnStart = true`：开局**一次性**把相机水平角对齐角色朝向（满足"一开始面朝同一方向"，但不持续跟随） |
| 俯角 | 基准 `_pitch = 40°`，鼠标在其上**上下偏移**。<br>可达范围 `[-13.5°, 80°]`（默认距离下）—— **可直接看到角色上方** |
| 俯角下限 | ⚠️ **不是固定值**，而是动态的「地面安全角」：`asin((groundY + clearance − focusY) / distance)`<br>距离 1.5/3/5/10 m → 下限 −27.8° / **−13.5°** / −8.1° / −4.0° |
| 地面钳制 | `_groundY` 开局自动探测（射线**忽略角色自身**）+ `_groundClearance = 0.3` |
| 距离 | `_distance = 3`，滚轮缩放 1.5~10 |
| 平滑 | `_smoothTime = 0`（**硬跟随**）—— 最不容易抖 |
| 开局 | `SnapToTarget()` 瞬移到位，避免从场景旧位置飞过来 |
| 鼠标指针 | `_lockCursorOnStart` 默认 false；勾上则锁定；⚠️ `Esc` 归**暂停菜单**（相机不再监听 `Esc`） |

**实测机位**：`(0, 2.93, -9.45)`、欧拉 `(40,0,0)`、到焦点 3.00 m；
相对玩家**水平 2.30 m / 上方 2.93 m**；角色屏幕 **x=0.500（居中）**。

#### ⚠️ 仰视与防穿地：为什么钳制「俯角」而不是「机位高度」

要允许仰视，就必须防相机沉到地面以下。两种做法：

| 做法 | 后果 |
|---|---|
| 钳制**机位高度** `y ≥ 地面+余量` | ❌ 会**压缩**相机到焦点的距离，极端角度下相机贴到角色身上；<br>且机位脱离视线后必须改用 `LookAt` 才能让角色居中 |
| ✅ 钳制**俯角**（本项目采用） | **距离保持不变**，机位仍从焦点沿视线推出 → **角色继续自动居中**（实测点积 = 1.000000） |

⚠️ **安全角必须随距离变化，不能写死常数**：距离越远，允许的仰角越小。
若把 −19.5° 写死，滚轮拉到 5 m 以上就会穿地（那里只允许 −8°）。

> ⚠️ 仍未做（按用户决定，细节优化后议）：**防穿墙**（相机贴墙时会穿进墙里）、
> 极端仰角 + 最近距离时相机与角色距离缩短（约 1.0 m，可能贴脸）。

#### ⚠️ 架构约束：三者互不驱动（否则 WASD 时视角会持续旋转）

**这是一条必须守住的约束**，违反后会得到一个很难查的 bug。

| 环节 | 由谁驱动 |
|---|---|
| 相机 yaw | **鼠标** |
| 移动方向 | **相机 yaw**（相对相机） |
| 角色朝向 | **移动方向** |

**闭环不存在。** 若把「相机 yaw」改为跟随「角色朝向」，三者就成环：

```
按 A(左移) → 角色转向左侧 → 相机也跟着转向左侧
           → 下一帧「左边」变成相对新视角 → 角色继续转 → 无限螺旋 ⚠️
```

**实测症状**：按住 WASD 时视角不停旋转，且方向越转越偏。

**因此**：
- `_followTargetYaw` **必须保持 false**（该开关保留但已加警告：仅在「角色不转向移动方向」时才可用）
- 想满足"一开始和角色面朝同一方向"，用 `_alignYawToTargetOnStart`（**开局一次性对齐**，非持续跟随）

> 同理提醒：`PlayerMotor` 是**只读**相机方向、从不写相机；相机也只在开局读一次角色旋转。
> 若日后要加"相机自动回到角色背后"的功能，**只能在角色静止时做**——移动中做必然成环。

> ⚠️ **几何约束（重要）**：「俯角 40° + 距离 3 m + 看向角色」三者同时成立时，
> 相机必然在焦点上方 `3·sin40° ≈ 1.93 m`、水平后方 `3·cos40° ≈ 2.30 m`。
> 所以**「上方一米」与该俯角不能同时满足**。
> · 要「水平后方 3 m + 上方 1 m」→ 俯角只能是 **18.4°**（`atan(1/3)`）
> · 要「俯角 40°」→ 相机就必须抬高（当前方案）

**⚠️ 相机抖动的根因不在相机，在移动**（已修复）：
| 问题 | 原因 | 修复 |
|---|---|---|
| **`groundStick = 0.1`** | 语义是「每帧下压米数」且**未乘 `deltaTime`** → 60fps 下等于每秒压 6 米，角色 Y 每帧微跳 | 改名 `groundStickSpeed = 2`（米/秒），乘 `deltaTime` |
| **`skinWidth = 0.08`** | 推荐 `radius×0.1 = 0.03`，超 2.6 倍 → CC 与地面碰撞解析不稳 | 改为 **0.03** |
| `Rigidbody.useGravity = true` | `isKinematic = true` 时重力不生效，语义混淆 | 改为 **false** |

**⚠️ 另一个抖动源（已移除）**：上一版的**防穿墙 `SphereCast` 每帧探测**，结果在命中/未命中间跳变时会让机位在近/远之间反复弹。已移除；若日后确实需要防穿墙，**必须以带阻尼的方式**加回，不能每帧硬切换。

⚠️ **连带必要改动：`PlayerMotor` 的移动方向是「相对相机」**（视角可旋转后必须如此，否则转视角后按 W 会往斜里走）。

**手感可调参数**（选中 Main Camera 的 `CameraFollow`）：

| 参数 | 当前 | 调整效果 |
|---|---|---|
| `_lookSensitivity` | **0.35** | 鼠标灵敏度（度/像素） |
| `_pitch` | **40** | **基准**俯角（鼠标在此上下偏移）。加 = 更俯视 |
| `_minPitch` | **−60** | 俯角下限（负值 = 允许仰视）。⚠️ 仅作设计上限，实际下限由地面安全角自动收窄 |
| `_maxPitch` | **80** | 俯角上限 |
| `_distance` | **3** | 远近 |
| `_focusHeight` | **1.0** | 视线焦点高度（看向身体何处）。⚠️ 调高它会**放宽**地面安全角（焦点越高越不怕穿地） |
| `_groundClearance` | **0.3** | 相机离地面的最小余量。太小会让近裁剪面切进地面 |
| `_groundY` / `_autoDetectGroundY` | **0 / true** | 地面高度；开启则开局自动探测（射线忽略角色自身） |
| `_smoothTime` | **0** | 位置平滑。加大会"跟手变软"，但可能重新引入抖动 |
| `_followTargetYaw` | **false** | ⚠️ 改 true 会重新引入「WASD 时视角持续旋转」的正反馈 bug（见下方架构约束） |

### 4.4 Boss（决策：**留到最后设计**）

## 5. ⚠️ 新方案有一个必须先解决的设计问题

> **"一条开阔通路 + 沿途小怪"意味着：玩家可以完全不打小怪，一路跑到 Boss。**

这不是 bug，是这类设计的固有特性。必须选一种处理方式：

| 方案 | 做法 | 代码成本 | 体验 |
|---|---|---|---|
| **A. 硬性封路（推荐）** | 每个遭遇区入口落闸，清完才开 —— **就是现有 `RoomController` 逻辑** | 🟢 **几乎为 0**（复用） | 节奏可控，最接近原设计的可靠性 |
| B. 软性阻拦 | 用敌人站位/狭窄地形自然阻挡，不强制 | 🟡 中（纯关卡设计） | 更自由，但会被跳过 |
| C. 不阻拦 | 允许跑酷直奔 Boss | 🟢 0 | ⚠️ 玩家会跳过你 80% 的设计内容 |
| D. 混合 | 多数区域软拦，Boss 前一个硬闸 | 🟡 中 | 平衡 |

**原决策：采用方案 C —— 不阻拦。** ❌ **已撤回（2026-10-05）**

> ⚠️ **撤回说明**：C 方案意味着"**玩家可以完全不打小怪，一路跑到 Boss**"（即下文的"已知代价"）。
> 这正是"**房间制白送的节奏控制被取消**"的具体表现 —— 最终决定回到有节奏的结构（多关卡独立场景）。
>
> ✅ **好消息**：`RoomController` / `DoorController` / `RoomTrigger` 这套"清完开门"的逻辑
> 因此在多关卡制下**继续承担节奏作用**，无需弃用。

### ⚠️ 关于"Boss 留到最后"的风险（已确认接受）

原始分析把 Boss 列为关键路径，理由是"它是整条路的目标"。
**采用 C 方案后这个风险显著降低**：因为不封路，玩家可以直接跑到终点，
**Boss 是"收尾"而不是"通关的必要条件"** —— 先做成一条能跑通、有战斗的完整通路，
最后再给终点补上 Boss，是**可接受的降风险做法**。

但要守住一条底线：

> ⚠️ **必须留出 Boss 的时间预算**。若通路搭完才发现时间不够做 Boss，
> 那就变成"一条路跑到尽头什么都没有"——**比原来的三房间更不完整**。
> 建议**在通路完成后立刻冻结功能**，把剩余时间全部投给 Boss。
