## 1. 先纠正一个前提：现在的敌人是"可见的白模"

这直接影响"路上放小怪"的观感判断，所以先说清。

| 预制体 | Renderer | 网格 | 材质贴图 |
|---|---|---|---|
| `Boxer` | 1 个 `SkinnedMeshRenderer` | `STYLIZED-BASEMESH-BIGMALE-OBJ` | ❌ **空**（`_BaseColor` 纯白） |
| `Gunner` | 1 个 `SkinnedMeshRenderer` | **同一网格** | ❌ 空 |
| `Enemy_Slime` | 1 个 `MeshRenderer` | Unity 内建球体 | ✅ `Mat_Slime` |

**所以敌人能跑能打能播动画，只是全白。** 这不阻塞玩法，但：

> ⚠️ **`Boxer` 和 `Gunner` 用完全相同的网格** → **当前实际只有一种敌人外观**。
> 单场景 ARPG 要"沿途一路小怪"，靠一种白模会显得重复。
> 💡 **低成本解法**：同一网格 + 不同材质（换色/金属度）+ 不同缩放 → 做出"小兵 / 精英 / Boss"的视觉层级。

## 2. 工作量：是"转移"不是"缩减"

这是本次决策最需要看清的一点。

| | 原方案（房间制） | 新方案（ARPG 单场景） |
|---|---|---|
| 关卡空间 | 3 间房（约 20×20 每间） | **1 条长通路**（需更长，含起始区/多个遭遇区/Boss 区） |
| 空间工作量 | 小（现有白盒） | **更大**（要设计路径、开阔地、隘口、Boss 场地） |
| 节奏设计 | ✅ **白送**——"清完开门"天然控制节奏 | ⚠️ **要手动设计**——敌人在哪、多少、怎么挡住玩家 |
| 区域逻辑代码 | 已有 `RoomController` | 🟢 **可复用**，改语义即可 |
| 敌人数量/波次 | 每房 1–2 个，简单 | ⚠️ 更多敌人同屏 → 要考虑**性能与对象池** |
| NavMesh | 3 间小房 | ⚠️ **更长更复杂**的导航网 + 巡逻 + 追击范围 |
| **Boss** | 3–5 天（原 M4） | 🟡 **同样 3–5 天，但决策改为"留到最后"**（C 方案下不再卡关键路径，但需守住时间预算） |

**结论**：代码省一点，**关卡与节奏设计要多花**。总量**持平偏增**。

> 关键点：**房间制把"节奏"这件事白送给你了**——玩家必须清完才能走，天然控制战斗密度。
> 单场景连续通路必须**手动设计节奏**（哪里放怪、是否封路），这是新增的设计成本。

## 4. 新增/要改的部分

### 4.1 关卡几何（新增）

- **场景**：新建一个关卡场景（或改造现有 `Game.unity`）
- ⚠️ **ProBuilder 未安装**（实测不可用）→ 要么用 **Cube 拼白盒**，要么装 ProBuilder
- 需要：起始区 → 通路（含开阔地与隘口）→ Boss 区；**沿途障碍物**（NavMesh 与视野遮挡依赖它们）

### 4.2 NavMesh（从"小"变"大"）

- 现状：**0 个 `NavMeshAgent`、导航网未烘焙**（实测）
- 新方案要：**整条通路一次性烘焙** + 敌人巡逻 + 追击边界（⚠️ 不能让敌人追出整张图）
- 详见 `NAVMESH-GUIDE.md`

### 4.3 敌人布置与节奏（新增的设计工作）

- 敌人**放置点 / 巡逻路径 / 触发式刷怪**
- ⚠️ **同屏敌人变多** → 需要评估性能（当前对象池只服务于特效，敌人是 `SetActive` 管理）

**决策：一路放 5–10 只小怪，外观由你提供新模型。**

摆放建议（配合 §5 的 C 方案）：
- 单只 → 稀疏散布在通路上（让玩家顺路顺手打）
- 2–3 只一组 → 放在**通路收窄处**（不封路，但很难绕过）
- 5–10 只的**总量**建议分布为：前期 1–2 / 中期 3–4 / Boss 前 2–4（最后一段加压）

#### ✅ 顺带的好消息：多了一套可用的行走/待机动画

你已把 Roskva 的 `.psa` 转成了 `OVR - Roskva_Animated.fbx`，里面有 **5 段动画**：

| 动画 | 时长 | 对 ARPG 的价值 |
|---|---|---|
| **`Walk`** | **3.08 s** | ⭐ **巡逻怪正好需要**（原动画库里只有跑，没有走） |
| `Idle01` | 46.67 s | 长待机素材 |
| `Talk01_old` / `Talk02` / `Talk03` | 36.7 / 41.7 / 46.7 s | 对话用，本项目用不上 |

⚠️ **但目前用不了**：该 FBX 的 Rig 是 **`Generic` 且没有 Avatar** → **动画无法重定向**。

✅ **已验证可以修**：这个 FBX 与玩家用的 `OVR - Roskva.fbx` **共享同一套骨骼命名**
（实测 16 个关键人形骨骼 `Bip001-Pelvis` / `Spine` / `Neck` / `Head` / 四肢 **全部一致**），
所以**只要在 Inspector 的 Rig 页把它也设为 `Human`，就能拿到 Avatar 并让这些动画可被复用**。
（操作：选中 FBX → Rig → Animation Type = Human → Apply）

> 💡 这意味着 **ARPG 的"巡逻小怪"不需要额外找走行动画**——直接用这段 `Walk` 重定向到敌人网格即可。

### 4.6 相机 ✅ **已实现**（2026-10-04）

**需求：跟随主角 + 鼠标控制视角 + 越肩视角。** 已完成（提交 `7c0cc3a` + 越肩改造）。

| 项 | 实现 |
|---|---|
| 跟随 | 焦点 = 玩家 + `_heightOffset(1.5)`（**肩/头高**，看向上半身） |
| **越肩** | `_shoulderOffset(0.9)` 把相机横移到右肩 → **角色落在屏幕左侧**（实测 x≈0.40） |
| 鼠标转向 | `_yaw` / `_pitch` 环绕；`Look`（已绑 `<Pointer>/delta`）驱动 |
| 俯角 | `_pitch = 18°`（**接近水平**，越肩必需）；限幅 **-10° ~ 70°** |
| 距离 | `_distance = 4.5`（**贴近**，越肩必需）；滚轮缩放 1.5~12 |
| 朝向 | **= 环绕旋转本身**，⚠️ **不是 `LookAt` 焦点** —— 用了 LookAt 会退化成"围绕角色的追尾相机"，取消掉越肩构图 |
| 平滑 | 只做在位置上（`SmoothTime 0.06`），角度即时响应 |
| 防穿墙 | 从焦点向机位做 **`SphereCast`**，撞到就把相机拉近（越肩距离近，走廊里必需） |
| 开局机位 | `Start()` 调 **`SnapToTarget()` 瞬移到位** —— 根治"从场景里的旧位置飞过来"导致的初始位置错误 |
| 暂停安全 | 用 `Time.unscaledDeltaTime`（结算 `timeScale = 0` 时相机不卡死） |
| 指针锁定 | `_lockCursorOnStart` 默认 **false**（编辑器调试方便）；勾上则锁指针，`Esc` 解锁、点击重锁 |

⚠️ **连带必要改动：`PlayerMotor` 的移动方向改为「相对相机」。**
视角能转之后，若仍用世界轴，**转视角后按 W 会往斜里走**，手感直接崩。
实现：把输入按相机的**前向/右向（投影到水平面）**换算成世界方向；朝向仍转向「移动方向」。

**手感可调参数**（选中 Main Camera 的 `CameraFollow`）：

| 参数 | 当前 | 调整效果 |
|---|---|---|
| `_lookSensitivity` | **0.35** | 鼠标灵敏度（度/像素）。偏钝就加 |
| `_shoulderOffset` | **0.9** | 越肩强度。**加 = 角色更靠边**，0 = 退回正后方追尾 |
| `_pitch` | **18** | 俯角。加 = 更俯视，减 = 更平视 |
| `_distance` | **4.5** | 远近。加 = 拉远看更多环境 |
| `_smoothTime` | **0.06** | 位置平滑。"发黏/跟不上"就减（0 = 硬跟随） |

## 5. ⚠️ 新方案有一个必须先解决的设计问题

> **"一条开阔通路 + 沿途小怪"意味着：玩家可以完全不打小怪，一路跑到 Boss。**

这不是 bug，是这类设计的固有特性。必须选一种处理方式：

| 方案 | 做法 | 代码成本 | 体验 |
|---|---|---|---|
| **A. 硬性封路（推荐）** | 每个遭遇区入口落闸，清完才开 —— **就是现有 `RoomController` 逻辑** | 🟢 **几乎为 0**（复用） | 节奏可控，最接近原设计的可靠性 |
| B. 软性阻拦 | 用敌人站位/狭窄地形自然阻挡，不强制 | 🟡 中（纯关卡设计） | 更自由，但会被跳过 |
| C. 不阻拦 | 允许跑酷直奔 Boss | 🟢 0 | ⚠️ 玩家会跳过你 80% 的设计内容 |
| D. 混合 | 多数区域软拦，Boss 前一个硬闸 | 🟡 中 | 平衡 |

**决策：采用方案 C —— 不阻拦。**

> ⚠️ **已知代价（已确认接受）**：玩家可以完全不打小怪，一路跑到 Boss。
> 缓解手段（不额外花成本）：把敌人**聚在通路收窄处**、并让它们 aggro 后**追击**——
> 现有 `EnemyMeleeAI` 已有追击逻辑（`aggroRange = 8`），跑过去也会被追着打，不会完全无代价。
>
> ⚠️ 副作用：`RoomController` / `DoorController` / `RoomTrigger` 这套"清完开门"的逻辑
> **在 C 方案下不再承担节奏作用**。可以先留着不用（不删），等关卡摆完再判断是否彻底移除。

### ⚠️ 关于"Boss 留到最后"的风险（已确认接受）

原始分析把 Boss 列为关键路径，理由是"它是整条路的目标"。
**采用 C 方案后这个风险显著降低**：因为不封路，玩家可以直接跑到终点，
**Boss 是"收尾"而不是"通关的必要条件"** —— 先做成一条能跑通、有战斗的完整通路，
最后再给终点补上 Boss，是**可接受的降风险做法**。

但要守住一条底线：

> ⚠️ **必须留出 Boss 的时间预算**。若通路搭完才发现时间不够做 Boss，
> 那就变成"一条路跑到尽头什么都没有"——**比原来的三房间更不完整**。
> 建议**在通路完成后立刻冻结功能**，把剩余时间全部投给 Boss。
