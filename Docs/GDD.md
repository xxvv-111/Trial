## 1. 游戏概述

### 1.1 一句话

俯视角 3D 动作游戏：玩家在一层由数个房间串成的试炼中连续清怪，用**普通攻击连段 + 武器专属特殊攻击**作战，靠**体力条**约束冲刺/攻击/特殊攻击的频率，最终击败 Boss 通关。

### 1.2 设计支柱

1. **动作手感优先** —— 连段、冲刺无敌帧、受击硬直，手感 > 内容量。
2. **体力即节奏** —— 一般移动免费，输出与位移收费。玩家必须在"打"与"撤"之间做取舍（这是本作与《哈迪斯》最核心的差异化点）。
3. **武器即流派** —— 每种武器一个专属特殊攻击，切换武器 = 换一套解题思路。
4. **敌我同规则** —— 玩家和敌人的攻击判定**都**由动画关键帧驱动的攻击碰撞体（hitbox）产生，规则对称、可读性强。

### 1.3 目标体验

- 单局时长 **5–8 分钟**。
- 玩家应能在 30 秒内理解操作，在 3 分钟内感受到"体力管理"的策略压力。
- 失败要"看得懂为什么输"（受击反馈清晰、体力见底有明确提示）。

## 4. 玩家角色

### 4.1 属性

| 属性 | 初始值 | 说明 |
|---|---|---|
| 生命上限 | 100 | 归零 → 死亡 → 失败结算 |
| 体力上限 | 100 | 见 §4.8 |
| 移动速度 | 6 m/s | 一般移动**不消耗**体力 |
| 冲刺速度 / 时长 | 10 m/s · 0.5 s | 冲刺期间无敌 |
| 冲刺无敌时长 | 0.5 s | 与冲刺时长一致 |
| 受击无敌 | 0.8 s | 受击后的保护时间 |

> 现状：以上除体力外，均已在 `PlayerConfig.asset` 中；受击无敌 0.8 s 硬编码在 `PlayerFSM` 内，⚠️ 建议移入配置。

### 4.2 移动

- 8 向移动，输入即朝向（`PlayerMotor`）。
- 固定斜角俯视相机跟随（`CameraFollow`，SmoothDamp）。
- **一般移动不消耗体力**。

### 4.3 跳跃 —— ❌ 已取消（决策记录）

- **决策**：**不做跳跃。** 理由：在本作的俯视角近战框架下，跳跃不解决任何战斗问题，收益低于成本。
- **连锁影响（重要，会改变工作量排序）**
  1. 省掉 `Jump` / `Fall` / `Land` 三组动画需求 —— 这是原计划里最大的动画缺口之一，取消后**美术压力显著下降**。
  2. **物理重构的紧迫性大幅下降**：`PROJECT-CONTEXT.md` 里的 **T1** 问题（`_motor.enabled = false` 把重力也一起停掉）原本被列为"加跳跃前必须先修"；取消跳跃后它**降级为低优先级**——代码仍不优雅，但不会阻塞任何功能。
  3. 体力消耗表移除"跳跃 15"一项。
  4. 敌人视野/寻路、Boss 瞬移等设计**无需考虑垂直维度**，实现更简单。

### 4.4 冲刺（已有，需接入体力）

- 触发：冲刺键（现有 `Dash` Action）。
- 位移 + 0.5 s 无敌帧，是主要的"闪避"手段。
- **消耗体力**。

### 4.5 普通攻击（已有 4 段连段，需接入体力 + hitbox 化）

- 4 段连段，伤害递增（12 / 15 / 10 / 20）。
- 连段窗口 1 s（`comboWindow`），动画事件 `OnAttackHit` 在关键帧触发伤害。
- **消耗体力**：按段递增。
- 改造点：由"瞬时 `OverlapSphere` 采样"改为"**帧驱动的攻击碰撞体**"（见 §8）。
  ✅ **已完成（M1.2）**：改为 `Hitbox` + `HitboxController` 常驻判定体；
  ✅ **M2.1 起**数值改由 `WeaponConfig` 提供（每把武器一套伤害/判定盒/连段窗口/体力消耗）。

### 4.6 特殊攻击 ⭐ 新增（两把武器的完整设计，已定）

- **每种武器一个**特殊攻击，两把武器都是**单次点按**触发。
- 差异化来自**效果本身**，而不是操作复杂度：剑是**近身范围爆发**，长枪是**中距离投掷 + 召回**。

**剑 · 插地（点按）**

- 点按特殊攻击键 → 角色将剑插入地面 → 以角色为中心爆发**圆形范围伤害**。
- 定位：被围困时的解围与清场手段。

**长枪 · 投掷与召回（点按投出，点按收回）**

| 阶段 | 行为 |
|---|---|
| **① 投掷** | **点按**特殊攻击键 → 立即投出，**没有蓄力、没有瞄准阶段** |
| **② 飞行** | 沿**直线**飞行（无抛物线），对**去程路径上的敌人**造成伤害 |
| **③ 落地** | 到达**固定投掷距离**（武器配置值）后**插在地上**，作为可见的世界物体留在原地 |
| **④ 空手** | 投掷后角色进入**"空手"状态**：**不能进行普通攻击**（仍可移动、冲刺） |
| **⑤ 召回** | 空手期间，**点按攻击键 或 点按特殊攻击键** 都能收回长枪 → 长枪**飞回**角色手中，对**返程路径上的敌人**造成伤害 |
| **⑥ 回手** | 长枪回手 → 解除空手状态，恢复普通攻击 |

- **"攻击键 = 召回键"的巧思**：空手期间攻击键**不执行攻击**（已被禁止），而是被**重新映射为召回**。所以"不能普攻"这条约束不会让玩家觉得"按键没反应"，而是按键**换了个用途**，操作直觉反而更好。
- **判定一致性（重要）**：投掷与召回的伤害**与其他攻击使用完全相同的判定方式** —— 同样走 §8 的**攻击判定碰撞体（hitbox）**，而不是另做一套"飞行物碰一下就扣血"的逻辑。这样伤害表现、飘字、特效都自然统一。
- **玩家死亡时**：若长枪尚未回收，**长枪就留在原地**（插在地上），流程直接进入结算面板；重开时随场景重置，不做特殊回收逻辑。
- 定位：中距离压制、多段收益（去程 + 返程各一次伤害）。

> ✅ **取消的设计（简化决策）**：原本设计的"长按蓄力 → 距离随蓄力增长 → 动态指示器 → 蓄力上限 → 瞄准减速"**全部取消**，改为**点按瞬间投出、固定距离**。
> 连带解决：不再需要"长按三态"输入支持、不需要投掷指示器 UI、不需要蓄力数值调参，"极短点按怎么办""瞄准是否降转向速度"等问题也一并消失。
> 代价：失去了"用蓄力做距离决策"的深度，换来实现与理解成本大幅下降。

> ⚠️ **"点按投出"带来的三个新细节（待确认）**
> 1. **投掷方向 = 角色当前朝向**（因为没有瞄准阶段了，所以是"朝哪扔哪"）。
> 2. **体力怎么收**：建议**投掷收 30、召回免费**。否则会出现"体力不足时付不起召回"→ 角色被卡在空手状态的尴尬局面。
> 3. **长枪尚在飞行途中能否立即召回**？还是必须等它落地插稳之后？建议**等落地**（状态更简单、表现更清晰）。

### 4.7 受击与死亡

- 受击 → 短暂硬直 0.8 s 无敌 + `Hit` 动画 → 回到移动。
- 死亡 → `Death` 动画（可用 root motion）→ 延迟 2 s → 失败结算面板。
- ⚠️ 现状问题：`PlayerHealth.Died` 事件从未被触发（早期代码被注释），真实死亡链路走 `PlayerFSM` → `GameEvents.RaisePlayerDied()`。改造时需统一。

### 4.8 体力系统 ⭐ 核心改动（原 mana 条）

**规则**

| 行为 | 体力消耗 | 备注 |
|---|---|---|
| 一般移动（走/跑） | **0** | 明确免费，保证"走位"永远可行 |
| 冲刺 | 20 | 起手瞬间扣 |
| 普通攻击 | 8 / 10 / 12 / 15（第 1–4 段） | 连段越深越贵 |
| 特殊攻击 | 30 | 武器可覆盖该值 |

**恢复**

- 停止消耗后 **0.6 s** 开始回复，回复速度 **25 / s**。
- ⚠️ 可选：命中敌人额外回复 5（鼓励进攻）。**待定**。

**体力不足时**（✅ 已定）

- **规则**：只要「动作的体力消耗 > 当前体力」，该动作**就不能执行**（硬性禁止）。规则统一、可预测，玩家能清楚知道"这一下我付不起"。
- **反馈**：动作不触发 + 明确提示（HUD 体力条闪烁 + 提示音）。
- **实现约束**：所有动作必须走**同一个体力检查出口**（`TrySpend(cost)` 语义），禁止任何动作绕过检查自行扣体力。
- **连段细则**：普通攻击连段中若体力不足以支撑下一段，则该段无法接续（前一段正常播完），避免"半截连段"的怪异表现。

**UI**：原 `ManaBar`（蓝色）改为体力条（建议改为绿色/黄色），位置与尺寸不变。

> ✅ **已解决（M1.1）**：此前"现有体力系统在游戏里**从未被真正消耗**（唯一调用点是调试作弊脚本）"——
> 现在成本表集中在 `PlayerEnergy`，接入 3 个消耗点（冲刺 / 普攻首段 / 连段后续），
> 体力不足则**硬性拒绝动作**，并含再生与 HUD 闪烁反馈。
> ✅ **M2.1 起**普攻与特殊攻击的成本改由 `WeaponConfig` 提供（成本表仍集中在 `PlayerEnergy`）。

### 4.9 玩家状态机

**状态列表**：`Idle`、`Run`、`Dash`、`Attack`、`Special`、`Hit`、`Death`
其中 `Special` 按武器内部分裂为子状态：`SwordSlam`（剑·插地）、`SpearThrow`（长枪·投掷）、`Unarmed`（长枪·空手，等待召回）、`SpearRecall`（长枪·召回）。

**主要转移**

| 从 | 到 | 条件 |
|---|---|---|
| Idle / Run | Dash | 冲刺键 且 体力 ≥ 20（已有） |
| Idle / Run | Attack | 攻击键 且 体力足够（已有） |
| Attack | Attack(下一段) | 连段窗口内再次按攻击 **且 体力足够**（已有 + 体力检查） |
| Idle / Run / Attack | Special | 持剑：**点按**特殊攻击键 → `SwordSlam`；持枪：**点按**特殊攻击键 → `SpearThrow` |
| SpearThrow | Unarmed | 投掷动作结束（长枪飞行 → 落地插地） |
| Unarmed | Attack | ❌ 不执行普通攻击；**攻击键被重新映射为召回** |
| Unarmed | SpearRecall | **点按攻击键 或 点按特殊攻击键** |
| SpearRecall | Idle / Run | 长枪回手，解除空手状态 |
| 任意（除 Death） | Hit | 受击且非无敌（**玩家与小怪**会被打断；**Boss 不会**，见 §6.1） |
| 任意 | Death | 生命 ≤ 0；若长枪未回手，**长枪留在原地**并直接进入结算 |

> 现状：`PlayerFSM` 用**三张字典（enter / update / exit）**驱动，扩展新状态只需加表项，**加 `Special` 及其子状态的成本很低**——这是沿用现有系统最大的红利。详见 §13。

| 特殊攻击触发 | 目前两把武器均为**点按**（若将来加入长按类招式，再扩展输入层） |
| 特殊攻击：伤害 / 范围或路径 / 体力消耗 / 冷却 | 每武器唯一 ✅ |
| 武器模型与握持挂点 | 右手骨骼挂点 + 外观模型（⚠️ 模型待补，先用无武器网格） |

### 5.3 V1 武器表（✅ 已定）

| 武器 | 普通攻击 | 特殊攻击 | 输入方式 |
|---|---|---|---|
| **剑** (Sword) | 四段；中等范围、伤害均衡 | **插地**：将剑插入地面，以自身为中心爆发**圆形范围伤害** | **点按** |
| **长枪** (Spear) | 四段；范围更长、单段伤害略低、判定更窄 | **投掷与召回**：点按**立即**直线投出（固定距离）→ 落地插地 → 空手不可普攻（**攻击键改为召回**）→ 点按攻击键或特殊攻击键召回（返程路径伤害） | **点按**（投出）/ **点按**（召回） |

> 两把武器都是**四段普通攻击**，因此可**共用现有 `Attack1–4` 动画**（见 §5.4），只需为两个特殊攻击各补少量动作。

### 5.4 动画方案 ⚠️ 关键决策

| 方案 | 做法 | 成本 | 建议 |
|---|---|---|---|
| **A. 共用动画 + 特效/数值区分** | 所有武器复用现有 `combo_01_1~4` 动画，靠特效颜色、伤害、判定范围区分 | 最低 | ✅ **V1 推荐** |
| **B. 每武器一套 controller** | 运行期换 `Animator.runtimeAnimatorController` | 中，需要成套新动画 | 若美术资源到位可升级 |
| **C. 动画层 + Avatar Mask** | 上半身按武器覆盖 | 高，调参复杂 | 不推荐 V1 |

> 现状：`PlayerAC.controller` 已有 `Locomotion`(BlendTree on `speed`)、`Attack1–4`、`Dash`、`Hit`、`Death` 共 8 个状态，参数 5 个。因为**两把武器都是四段**，`Attack1–4` **可直接复用**；需新增的是特殊攻击相关状态（`SwordSlam`、`SpearAim`、`SpearThrow`、`SpearRecall`）及其动画。

## 6. 敌人设计

### 6.1 通用规则

- **感知 = 距离 + 视野判定**（✅ 已定，不再只靠距离）
  - **视野范围**：一个扇形（`视野角度` × `视野距离`）。
  - **视线遮挡**：对玩家做射线检测，被墙/障碍物挡住 → **看不见**（判定失败）。
  - **发现条件**：玩家在扇形内 **且** 视线无遮挡 → 转入追击。
  - **丢失目标**：持续看不到一段时间后 → 进入"搜索/失去目标"状态（⚠️ 搜索行为细节待定：原地警戒 or 走到最后已知位置）。
  - ⚠️ 待定：是否给玩家"潜行/背刺"收益（如背后被发现更慢）——V1 建议不做。
- **两级距离**
  - **追击范围**（较大）：玩家进入并**被看见**后转入追击。
  - **攻击范围**（较小）：进入后可发起攻击。
- **保持距离**：敌人**不应贴脸**（本条需求的重点）—— 近战在攻击后短暂拉开，远程维持一个"舒适区"。
- **寻路**（✅ 已定）：敌人**必须能绕过房间里的障碍物接近玩家**，不能直线穿墙或卡在障碍物上。方案见 §6.5。
- **受击打断（✅ 已定：分两档）**
  - **普通小怪（剑兵 / 弓兵）：会被打断。** 受击进入 `Hit` 状态 → 硬直（约 0.4 s）+ 闪白，**硬直期间不行动，正在进行的攻击被打断**。玩家可以用连段压制小怪，清怪手感更爽。
  - **Boss：不会被打断。** 受击只闪白（可加受击特效），**行动完全不中断**；也**不引入**"硬直条 / 破防"机制。
  - **设计意图**：小怪可压制 → 割草爽感；Boss 不可压制 → 只能靠躲避与抓空档，把考核集中在 Boss 战。
  - ⚠️ **与现有代码的冲突（必须处理）**：注意这里**不是"删硬直"，恰恰相反**。`EnemyMeleeAI` 里虽然写了受击硬直（`EState.Hit` + `_stunT = 0.4f`）、击退（`KnockBack`）、闪白（`FlashRed`），但这些**全是死代码**：`EnemyMeleeAI` 的 `TakeDamage` 早已被注释掉，而且它**根本没有实现 `IDamageable`**。玩家攻击命中的是 `EnemyHealth`（`PlayerAttack` 里 `hit.TryGetComponent<IDamageable>()`），而 `EnemyHealth.TakeDamage` **只扣血，从不通知 AI**。
    → **现状：小怪挨打毫无反应**（连闪白都不会触发。玩家侧只能看到打击火花与伤害飘字）。
    → **要做的事：把这条链路接通**，让 `EnemyHealth` 受击时通知 AI 进入 `Hit`。详见 `PROJECT-CONTEXT.md` 的 **T21**。
- **死亡**：播放死亡动画 → 通知房间计数（现有 `EnemyHealth.Died` 事件链路可用）。
- **敌人之间不重叠** ⚠️ 可选（简单分离力即可，提升观感）。

### 6.2 剑兵（Swordsman，近战）⭐ 新增

| 项 | 值（草案） |
|---|---|
| 生命 | 45 |
| 追击范围 | 12 m |
| 攻击范围 | 1.8 m |
| 移动速度 | 3.2 m/s |
| 攻击前摇 / 后摇 | 0.45 s / 0.5 s |
| 伤害 | 12 |
| 攻击后拉开距离 | 攻击结束退后 1.5 m（避免贴脸） |

**行为状态机**

```
Idle ──玩家进入追击范围 且 视野内可见──> Alert(转朝向、短暂停顿)
Alert ──> Chase（寻路接近玩家，直到进入攻击范围）
Chase ──距离 ≤ 攻击范围──> Windup（前摇）
Windup ──前摇结束──> Attack（关键帧激活 hitbox）
Attack ──> Recover（后摇）──> Reposition（退后 1.5 m）──> Chase
任意 ──受击──> Hit（硬直 0.4 s + 闪白）──> Chase
任意 ──生命 ≤ 0──> Death
```

> ✅ 剑兵**会被打断**（见 §6.1）：受击进入 `Hit` 硬直，正在进行的攻击中断。所以剑兵不依赖"夸张前摇"来给玩家反应时间——玩家可以直接用连段压制它。

**动画状态机**：`Idle`、`Run`、`Attack`、`Hit`、`Death`（各状态用 Trigger/Bool 驱动）

> 现状：`EnemyMeleeAI` 已有 `Idle/Chase/Attack/Hit/Death` 五状态（switch 实现），是很好的起点，但**缺少 Alert / Reposition**，且动画触发写在 `Update` 里（每帧 `SetTrigger`，属隐患）。敌人动画状态机 `EnemyAC.controller` **目前只有 2 个状态**（`idle`、`combo_01_1`），必须扩充。

### 6.3 弓兵（Archer，远程）⭐ 新增

| 项 | 值（草案） |
|---|---|
| 生命 | 30 |
| 追击范围 | 14 m |
| 射击距离 | 4 – 9 m（在此区间内可射） |
| 舒适距离 | 6 m（小于此值则后撤） |
| 移动速度 | 2.8 m/s |
| 射击冷却 | 2.2 s |
| 伤害 / 弹速 | 8 / 14 m/s |
| 瞄准前摇 | 0.5 s（有明显预警，给玩家反应时间） |

**行为状态机（含"保持距离"核心逻辑）**

```
Idle ──玩家进入追击范围 且 视野内可见──> Alert
Alert ──> Reposition（用寻路移动，且要考虑障碍物）：
          · 距离 < 舒适距离(6m) ──> BackOff（后撤远离玩家）
          · 距离 > 射击距离(9m) ──> Approach（靠近）
          · 在 6–9m 区间 ──> Strafe（横向绕行，避免站桩）
Reposition ──在射击区间 且 冷却就绪 且 视线无遮挡──> Aim（前摇 0.5s，转向玩家）
Aim ──> Shoot（生成箭矢，关键帧放箭）──> Cooldown ──> Reposition
任意 ──玩家贴脸(< 3m) ──> BackOff（优先脱离）
任意 ──受击──> Hit（硬直 0.4 s + 闪白）──> Reposition
任意 ──生命 ≤ 0 ──> Death
```

> ✅ 弓兵同样**会被打断**（见 §6.1）。⚠️ 注意一个手感细节：如果弓兵在 `Aim`（瞄准前摇）阶段被打断，**建议直接取消这次射击**而不是"硬直结束后继续放箭"，否则会出现"明明被打断了却还是射出一箭"的欺骗感。
> 另注：弓兵的射箭也应**检查视线遮挡**（被柱子挡住就不应射击），否则会出现"箭穿过障碍物"的观感问题。

**动画状态机**：`Idle`、`Run`（移动/后撤共用）、`Aim`、`Shoot`、`Hit`、`Death`

> 现状：`EnemyRanged` **完全没有状态机**（只有一个冷却计时器 + 转向 + 开火），需要从零搭。可复用的零件：`Bullet`（弹道 + 命中判定）、`EnemyHealth`（血量/死亡事件）。

### 6.4 敌人共性架构建议

两种敌人应共用一套**敌人状态机基类**（状态表驱动，与玩家 FSM 同风格），差异只在"状态集合 + 转移条件 + 数值"。这样加第三种敌人（如盾兵）几乎是纯配置工作，报告里也能体现"可扩展性"这一设计目标。

### 6.5 寻路方案（✅ 已定：**Unity 自带 NavMesh**）

> 房间内**布置了障碍物**，直线追击会被卡住，因此敌人必须有真正的寻路。两条路的对比保留在下方，作为报告"方案选型"的素材。
>
> **📘 操作手册见 `NAVMESH-GUIDE.md`**（手把手教学：烘焙、Agent 改造、门的动态阻挡、kiting 正确写法、常见坑速查）。本节只讲**为什么这么选**。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 接入自研 A\*（**已弃用**） | 用房间里障碍物的包围盒生成**网格**（标记可行走格）→ 调用已实现的 `AStar.FindPath` 求路径 → 路径平滑（拉直）→ 沿路径移动 | 报告含金量高：可写"自行实现 A\* 并接入游戏" | ⚠️ **有硬缺陷**：`AStar.FindPath` 不重置邻居节点的 `G/F/Parent`，复用同一网格重算会因残留 `Parent` 成环导致 `Reconstruct` **死循环卡死编辑器**（而第 6 条要求"每 0.3 s 重算"必须复用网格）→ **不加 Reset 就不能接入**。此外工作量大：需自建网格烘焙、障碍物标记、路径平滑、动态避障 |
| **B. Unity 自带 NavMesh** ✅ **已选** | `com.unity.ai.navigation` **2.0.14 已安装**：烘焙 `NavMeshSurface` + `NavMeshAgent` 移动 + `NavMeshObstacle`(carving) 处理动态门 | 省事、移动平滑、自带避障（RVO）与区域代价，**无上述死循环风险** | 算法含金量低，报告只能写"使用引擎导航" |

**为什么改（✅ 决策记录，2026-10-04）**

1. **自研 A\* 存在阻断性缺陷**（见上表 A 的缺点列），修好它本身就是额外工作量，且修好后仍要面对第 2 条。
2. **NavMesh 把自研方案里最耗时的四件事全部内置**：网格烘焙、障碍物标记、路径平滑、动态避障。
3. **效果上限更高**：NavMesh 自带 RVO 避障与区域代价，自研要达到同等水平远超课设预算。

⚠️ **代价与补救（重要）**：报告里**不能再写"自行实现 A\* 并接入游戏"**。
→ 🔧 **补救方案**：`AStar.cs` 与 `Editor/AStarSelfTest.cs` **保留不动**，在报告中作为**独立的"路径搜索算法实现"章节**（原理 + 自研 `Node` 结构 + 曼哈顿启发式 + 4 邻域），并把 `Tools/A* 自测`（5×5 绕障、校验不穿墙）与 `Tools/A* 自测2：无路`（整列堵死返回 `null`）**两个用例截图当测试证据**。实际运行方案则在"工程选型"章节另述。
这样"算法能力"与"工程判断力"两头都能写 —— 能说明**为什么放弃自己写的东西**，反而是加分项。

**实现要点（按 B 方案 → 详见 `NAVMESH-GUIDE.md`）**

1. **烘焙**：新建 `NavMeshRoot` 挂 `NavMeshSurface`，`Agent Radius 0.4 / Height 2.0`（与实测敌人碰撞体一致），`Use Geometry = Physics Colliders`（本项目墙/地是 Cube+BoxCollider 白盒），点 Bake。
2. **障碍物**：⚠️ 房间内**目前没有任何障碍物**，需先摆 3–6 个静态 Cube（柱子/箱子），位置故意卡在"玩家—敌人连线上"，**摆完必须重新 Bake**。
3. **移动改造**：敌人加 `NavMeshAgent`，**删除 `EnemyMeleeAI.MoveTowardPlayer()` 里的 `transform.position +=`**（否则两者打架，表现为抖动/瞬移）；攻击时用 `_agent.isStopped = true`（⚠️ 不是已过时的 `Stop()`）。
4. **门的动态阻挡** ⚠️：`DoorController.Open/Close()` 只是 `_body.SetActive()`。门若被烘焙进 NavMesh，开门后导航网**不会自动更新**，敌人仍会绕路。→ 给门挂 `NavMeshObstacle` 并勾 **`Carving`**，并从 `NavMeshSurface` 的 Include Layers 中排除门体。
5. **兜底**：`NavMesh.SamplePosition` 找合法落点；找不到时 `ResetPath()` 原地待机，**不允许卡死**。
6. **性能**：Agent 自带 `autoRepath`，不要每帧手动重算路径。

> ⚠️ **注意：NavMesh 只解决"怎么走到某点"，不解决"该走哪"。**
> "**远程敌人保持距离（kiting）**"**不能**只靠寻路解决 —— 需要上层状态机主动选一个"远离玩家的目标点"，用 `NavMesh.SamplePosition` 吸附到合法点后，再把那个点交给 Agent。**直接把 `player.position` 丢给 `SetDestination` 会让弓兵冲向玩家，是完全错误的写法。**
> 另：⚠️ 视野扇形与视线遮挡（§6.1）**NavMesh 不提供**，仍需自写 `EnemyPerception`（扇形角度 + `Physics.Raycast`）。

### 7.2 行为决策（需求核心）

Boss 不只是"接近 → 打"，而是**读玩家的行为**选招：

| 玩家行为 | Boss 反应 |
|---|---|
| 玩家在**近距离**缠斗 | 近战横扫（大范围）+ 快速连击 |
| 玩家从**近距跑到远距**（如 距离由 <5m 变为 >10m 且持续 0.5 s） | **瞬移冲刺追击**（TeleportDash：消失 → 出现在玩家附近 → 冲刺斩） |
| 玩家在**中距离**保持 | 跳跃砸地（AOE 圆形判定） |
| 玩家**远距离站桩**（>12m 且不靠近） | 远程投射（弹幕/地面裂痕） |
| 阶段 2 | 攻速提升 + 新增招式 + 部分招式判定范围扩大 |

### 7.3 状态机草案（两层）

- **决策层**：周期性（或事件驱动）评估"玩家距离模式" → 选择一个招式。
- **招式层**：每个招式是一个子状态机（前摇 → 判定 → 后摇 → 冷却）。

```
Idle → Approach / Evaluate
Evaluate ──选择──> MeleeCombo | TeleportDash | SlamAOE | Projectile
MeleeCombo / TeleportDash / SlamAOE / Projectile ──结束──> Cooldown → Evaluate
任意 ──生命 ≤ 50% ──> PhaseTransition（短无敌 + 表现）→ Phase2 的 Evaluate
任意 ──生命 ≤ 0 ──> Death（长演出) → 触发胜利结算
```

> ✅ **Boss 不会被打断**（见 §6.1）。注意：**普通小怪是会被打断的，只有 Boss 例外** —— 所以原本设想的"硬直条 / 破防"机制**不引入**，`Stagger` 状态从草案中移除。Boss 的行动完全由自身决策层驱动，玩家只能躲避、抓空档，不能压制。
> ⚠️ 因此 **Boss 的攻击前摇（预警表现）必须做足**：它是玩家面对 Boss 时唯一的反应窗口，直接决定 Boss 战是否"打得明白"。

## 8. 战斗判定系统（重点技术设计）⭐

### 8.1 需求

> 不论敌人还是玩家的攻击，攻击范围都应通过在**动画中找到关键动作帧**，然后根据这个动作**创建一个判定攻击的碰撞体**来实现。

即：判定不是"按键瞬间采样一次"，而是"**在动画的特定时间窗内，存在一个真实存在的碰撞体**"。

### 8.2 方案

**组成**

1. `Hitbox`（挂在角色子物体上）
   - ` Collider`（`isTrigger = true`，形状随武器/招式不同：盒/球/胶囊）
   - 字段：伤害、所属阵营（玩家/敌人）、单次攻击是否只命中同一目标一次、所有者引用
   - 内置"已命中目标集合"，避免同一次挥砍对同一目标重复扣血
2. 开关控制（二选一或结合）
   - **方式 A：Animation Event** —— 在关键帧调用 `EnableHitbox("Attack1_Phase1")` / `DisableHitbox()`
   - **方式 B：StateMachineBehaviour** —— 状态 enter 开启、exit 关闭（**推荐主用**，美术改动画时不会漏挂事件）
   - **建议：B 为主 + A 为辅（用于一招多段的中间帧）**
3. `HitboxController`（每个角色一个）
   - 管理本角色所有 hitbox 的注册、按名开关、当前激活列表
   - 统一处理 `OnTriggerEnter` → 过滤阵营 → 调用目标 `IDamageable.TakeDamage()` → 播放打击特效/飘字
   - 提供 `OnDrawGizmos` 可视化（调试时能"看见"判定范围）

**分层与碰撞矩阵**

| Layer | 用途 |
|---|---|
| `Player` | 玩家本体 |
| `Enemy` | 敌人本体 |
| `PlayerHitbox` | 玩家的攻击判定 |
| `EnemyHitbox` | 敌人的攻击判定 |
| `Projectile` | 箭矢/弹幕 |
| `Environment` | 墙、地面 |

矩阵要点：`PlayerHitbox` 只与 `Enemy` 碰撞；`EnemyHitbox` 只与 `Player` 碰撞；hitbox 之间互不碰撞。

### 8.3 为什么现在就能做（利好）

现有架构**已经预埋了这条通道**：
- `PlayerAttack` 已通过**动画事件** `OnAttackHit`（挂在 `combo_01_1~4` 上）触发伤害。
- `EnemyMeleeAI` 已通过**动画事件** `TickAttack`（挂在 `enemy/combo_01_1` 上）触发伤害。

也就是说，需要做的不是"引入动画事件机制"，而是把**动画事件里的"瞬时采样"升级为"持续存在的碰撞体"**——架构方向一致，改动是收敛的。

- 编辑器校验菜单：扫描所有攻击动画，列出"有 hitbox 开关事件 / 无"的清单，防止漏配。

### 11.2 存档方案 ⚠️ 待你选择（下方含两种方式介绍）

**存档内容（先定内容，再定方式）**

| 内容 | 说明 |
|---|---|
| 最好通关时间 | 开始界面与胜利/结束界面展示 |
| 通关次数 / 死亡次数 | 统计展示（可选） |
| 音量设置 | 主音量 / BGM / SFX |
| 最后使用的武器 | 下次进入默认沿用（可选） |

**方式 A：`PlayerPrefs`（Unity 内置键值对）**

- 原理：Unity 自带的键值存储，Windows 上实际写进**注册表**（`HKEY_CURRENT_USER\Software\<公司名>\<产品名>`）。
- 用法：`PlayerPrefs.SetInt/SetFloat/SetString(key, value)`、`GetInt(key, 默认值)`、`Save()`。
- 优点：**代码量极小**（几行就能用）；跨平台；路径与权限由引擎处理，不会因目录不存在而报错。
- 缺点：只能存 `int / float / string` 三种标量，复杂结构要自己拆；**Windows 上不产生可见文件**（答辩时无法"打开文件给老师看"）；调试时看不到内容；没有版本号，将来改结构会读到脏数据。
- 适合：**少量标量**（音量、最好成绩）。

**方式 B：JSON 文件（写到磁盘）**

- 原理：C# 对象 → JSON 字符串 → 写文件。路径用 `Application.persistentDataPath`（Windows 上是 `C:\Users\<用户名>\AppData\LocalLow\<公司名>\<产品名>\`）。
- 用法：`JsonUtility.ToJson(obj)` / `JsonUtility.FromJson<T>(text)`（Unity 内置，无需第三方）+ `File.WriteAllText/ReadAllText`。
- 优点：能存**任意复杂结构**（数组、嵌套对象、统计列表）；**会产生一个真实可见的存档文件**（答辩时能打开展示，很加分）；可加**版本号**做存档迁移；可加密/加校验；甚至能手动改文件来调试。
- 缺点：代码量比 A 多一些（要处理"文件不存在 / 内容损坏 / 读写异常"）；要自己管路径与目录；`JsonUtility` 有局限（**不支持 `Dictionary`**、`null` 处理较怪、不能直接存多态）。

**✅ 已定：用方式 B（JSON）统一存全部数据**（用户已确认）。
理由：课程设计里"数据持久化"是能写进报告的一章，答辩时有实物文件可展示；而且将来要加"统计列表/解锁状态"时不用推倒重来。

**实现要求**

- 存档类带 `version` 字段，为将来格式变更留迁移余地。
- 读写必须包 `try/catch`：**文件不存在**（首次运行）→ 用默认值；**内容损坏** → 用默认值并覆盖写回。
- 路径用 `Application.persistentDataPath`，**不要**用 `Application.dataPath`（Assets 目录，打包后只读，会失败）。
- 序列化用内置 `JsonUtility`。⚠️ 注意它**不支持 `Dictionary`**、不能直接存多态，存档结构里避免这两类。
- 存盘时机：通关 / 死亡结算时写一次；设置变更时写一次。不必每帧写。

## 16. 附录：术语表

| 术语 | 含义 |
|---|---|
| **hitbox** | 攻击判定碰撞体，动画关键帧期间存在 |
| **hurtbox** | 受击判定体（本作 V1 直接复用角色本体 Collider） |
| **前摇 / 后摇** | 攻击生效前 / 后的不可取消时间段 |
| **无敌帧 (i-frame)** | 期间免疫伤害 |
| **连段窗口** | 允许接下一段攻击的时间段 |
| **kiting** | 远程单位保持距离、边打边退的行为 |
| **Blend Tree** | 动画混合树（本项目 `Locomotion` 按 `speed` 混合） |
| **重定向 (Retargeting)** | 把一套动作套用到另一具 Humanoid 骨骼上 |
| **白盒 (Greybox)** | 用基础几何体搭的临时关卡 |
